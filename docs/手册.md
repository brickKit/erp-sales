## 3. 完整契约清单

**gRPC `erp.sales.v1.SalesService`**（9 个 rpc，见 `contracts/erp/sales/v1/sales.proto`）：

| rpc | 类型 | 暴露到 REST？ |
|---|---|---|
| `CreateOrder` | 写，建 DRAFT，不预留库存 | ✅ `POST /erp/sales/orders` |
| `ConfirmOrder` | 写，TCC 链 | ✅ `/erp/sales/orders/{id}/confirm` |
| `CancelOrder` | 写 | ✅ `/erp/sales/orders/{id}/cancel` |
| `ShipOrder` | 写 | ✅ `/erp/sales/orders/{id}/ship` |
| `CalculatePriceDryRun` | 读，纯函数不落库 | ✅ **必须暴露**，前端下单页实时试算 |
| `GetOrder` / `ListOrders` | 读，游标分页 | ✅ `/erp/sales/orders[/{id}]` |
| `BatchGetOrder` | 读 | ❌ 只给组件间 gRPC 客户端防 N+1 用 |
| `GetOrderStatus` | 读 | ❌ 组件间协议，防"薛定谔的超时" |

**发布事件：** `sales.order.created.v1`（⚠️ 在 `ConfirmOrder` 成功后发，不是 `CreateOrder`）、`sales.order.cancelled.v1`、`sales.order.shipped.v1`。
**消费事件：** `finance.credit.rejected.v1`（权威额度超限→`SUSPENDED`）、`mdm.customer.created.v1`/`.updated.v1`（维护 `customer_snapshots.credit_limit`）、`infra.workflow.task.completed.v1`（阶段三，补偿异常待办被人工确认 `action==APPROVED` 时把订单从 `SUSPENDED` 恢复回 `DRAFT`，见设计计划 §3.1、§4.4.4——只处理 `source_component=="erp/sales"` 的记录）、`crm.opportunity.won.v1`（阶段三 Task 14 落地：赢单自动转订单，`backend/internal/tcc/opportunity_won.go` 的 `HandleOpportunityWon` 编排建单+确认，走系统身份客户端 `client.*System`——事件 handler 语境没有 JWT 可透传，归属字段（`owner_id`/`dept_path`）从事件本身取而不是 `besdk.ScopeOf(ctx)`；任何一步失败都建一条 `infra-workflow` 异常待办通知事件里的 `owner_id`，不回传失败给 `crm-opportunity`）。⚠️ **不消费** `finance.voucher.posted.v1`——它没有 `customer_id`，这条契约缺口已经在设计计划 §9 第 6 条记录，`customer_snapshots.credit_exposure` 的新鲜度完全交给定时对账。

**依赖**（四条强 + 一条弱，本组件是阶段二唯一有依赖的组件）：`mdm/customer@1.0.3`、`mdm/product@1.0.3`、`erp/inventory@1.0.6`、`erp/finance@1.0.3`（强）+ `infra/workflow@1.0.1`（弱，`optional: true`，阶段二真实不存在，**阶段三已建成并真机接通**：`CreateTask` 建异常待办 + 消费 `task.completed.v1` 恢复订单）。**真机验证过**：`brickkit up --dry-run` 正确生成拓扑顺序（`erp-sales` 排最后，依赖前四个）、正确对缺失的弱依赖只发警告不阻断。

详细字段与判据见设计计划 `docs/design/erp-sales.md` §3、§4、§5——那份是真相源，这里是速查表。
